12

r1_constants.py — the robot

Job: walk all six sections of one file, each in one line of what + why.
Section 1

MJCF + get_spec() — points at the GMR-clean R1 model, no phantom joints

What it means

Reuses week 22–27's own finding (the phantom waist/wrist joints) rather than re-deriving it — this file inherits that already-solved problem for free by building on the GMR model.

Section 2

Actuator configs (7 groups) — stiffness, damping, effort_limit per joint-torque class

What it means

These three numbers, repeated seven times (once per motor class), are the entire physical identity of simulated R1 — how stiff, how damped, how strong each joint is.

Sections 3–4

STAND_KEYFRAME — the already-validated Goal-1 pose · FULL_COLLISION — feet get real contact, everything else self-collision only

What it means

Both sections are reuse, not new invention: the standing pose from Goal 1, and a contact scheme (feet=condim 3, body=condim 1) that's the standard convention across this project's MuJoCo work.

Sections 5–6

get_r1_robot_cfg() — assembles everything, fresh instance every call · R1_ACTION_SCALE — computed as 0.25 × effort_limit / stiffness per joint

What it means

The action-scale formula is the one piece of real arithmetic in this file — it's what turns a policy's raw, roughly-unit-scale output into a physically sensible joint-position nudge.

Sim2sim, honestly

Body paragraph

What it means

The last clause matters most: it rules out the easy version of this test (just switching a "device=cpu" flag inside the same simulator) in favor of the harder, more meaningful one — genuinely different solver code.

Left card

What it means

The harness still diverges closed-loop; two more real tests followed, on the next slide.

What it means

This card grew from "one bug, one open question" (the first debugging pass) to "four bugs, a proven-correct formula, still open" (after a second pass) — the honest update, not a rewritten history. Sim2sim, continued

Job: run the two remaining hypotheses as real tests, not as speculation.
Subtitle

two more real tests, and where this actually lands

What it means

Both tests were genuinely run, not reasoned about in the abstract — an extended-training checkpoint and a backend-matched inference path, each with real before/after numbers.

Terminal — extended training

Resumed to model_12998.pt (+10,000 iters), 3:19:10 wall time. Native: success_rate 0.9688→0.9844, mpkpe 0.2991→0.1588 (nearly halved). sim2sim: mean joint_pos_error 4.79→4.59 rad (~4% better)

What it means

The key contrast in this row: native performance improved dramatically (mpkpe nearly halved) while the sim2sim error barely moved (~4%). If undertraining were the cause, closing most of the native gap should have closed most of the sim2sim gap too — it didn't.

Terminal — CUDA-policy test

Swapped onnxruntime/CPU inference for the raw PyTorch checkpoint on CUDA (matching what native training actually used): mean joint_pos_error 4.70 rad — no meaningful change
